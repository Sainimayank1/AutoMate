# Dashboard (M1): design and integration

The command centre for the selected vehicle. Product scope: [MODULES.md M1](../MODULES.md#module-1--dashboard); money rules: [expenses.md](expenses.md); look: Stitch "Dashboard — Desktop / Mobile" through the `automate-design` skill.

**Ownership:** the dashboard owns no records and no business logic. It asks each module's service for figures (Expenses for money, Fuel's engine for mileage, Vehicles for the odometer) and lays them out. A number on the dashboard is always the same number the module shows.

## 1. Rules

- **One vehicle at a time** (the active vehicle, switchable). Every query is scoped to the signed-in user and checks the vehicle is theirs.
- **Truthful data:** no invented scores or trends. "No issues recorded" is not "healthy": while maintenance and documents aren't tracked, the status panel says **Vehicle health information incomplete** and lists what isn't tracked.
- **Money** follows [expenses.md §1](expenses.md#1-cost-classes-and-the-three-money-views): refunds netted, linked records (fill-ups) counted once, unpaid scheduled payments never counted.
  - **Spent** = everything paid on the vehicle, net of refunds, **excluding loan principal** (running cost + insurance and taxes + loan interest and charges + accessories).
  - **Running cost / km** = running (`OPERATING`) cost ÷ km, as in Expenses.
- **Mileage** only from Fuel's full-tank engine (`computeMileage`), in the fuel's unit (km/L, km/kg, km/kWh), with the number of full-tank cycles it rests on.
- **Distance** comes from odometer readings (fill-ups and expenses) and is labelled so; trip distance is never added to it.
- **Comparisons** use a window of the same length: this month to date is compared with the same days of last month, never with all of last month. No percentage when the earlier value is 0; no comparison when either side lacks data, or when records start inside the earlier window (it is only partly on record: money and distance aren't compared, mileage still is, since its full-tank cycles are whole).
- **Smart insights** (`insights.ts`) are fixed rules over figures the other sections already have, never AI and never a number of their own. Each says why (the figures), against what (the comparison window, or the run of full tanks or months), how sure (by full-tank cycles or odometer readings, where that varies) and where to look. A change must clear a threshold (`THRESHOLDS`: e.g. spending ±10% and ±₹500, distance ±15% and ±100 km) and both sides must be on record; spending is compared only once records reach back to the start of the earlier window. One insight per topic, costs and worse running first, at most 4; when records are missing it says which (`needs`), and "Nothing stands out" when nothing clears the bar.
- **Partial data:** each section is computed on its own; a failing section returns an error state (with retry) and the rest still renders. Sections of modules that aren't built yet stay hidden.

## 2. Periods (IST)

| Period               | Window                   | Compared with                           |
| -------------------- | ------------------------ | --------------------------------------- |
| This month (default) | 1st of the month → today | The same days of last month             |
| Last month           | The whole previous month | The month before it                     |
| Last 3 months        | 3 months ending today    | The same number of days just before it  |
| This year            | 1 January → today        | The same days of last year              |
| Last 12 months       | 12 months ending today   | The same number of days just before it  |
| Custom               | From → to (inclusive)    | The window of the same length before it |

## 3. API

| Route                       | Notes                                                                                                                                                                                                                                                                                                                                                                                                     |
| --------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /dashboard/overview`   | `vehicleId`, `period`, `from`/`to` (custom). One response: the vehicle, the period with its comparison window, and one entry per section (`status`, `metrics`; more each phase), each `ok`, `empty` or `error`. Custom ranges: `periodQueryFields` + `checkPeriodQuery` (shared), 2000 → today (IST).                                                                                                     |
| `GET /dashboard/activity`   | Paginated feed of the vehicle's fill-ups, expenses, refunds and service records, newest first (the latest `ACTIVITY_DEPTH` = 96), each linking to its record. Maintenance-sourced expenses are left out: their service record stands for them.                                                                                                                                                            |
| `GET/PUT /dashboard/layout` | The signed-in user's layout: every section once, in order, shown or hidden, and the chosen key figures (at least one). Saved in `user_preferences.dashboard` (JSON: an opaque, never-filtered payload, validated by `dashboardLayoutSchema`); read back through `normalizeDashboardLayout`, so a section added later appears where the default has it. The default until saved; reset = save the default. |

## 4. Phases

1 · Foundation (route, header with vehicle and period selectors and refresh, overview endpoint and period logic, page states) → 2 · Section frame and grid, vehicle hero, status and core metrics → 3 · Expense and fuel analytics → 4 · Documents and usage → 5 · Action centre, activity and quick actions → 6 · Smart insights (deterministic rules, no AI) → 7 · Customisation → 8 · Polish. Each phase is approved before the next.

**Built:** phase 1 (route, greeting header with the active-vehicle and period selectors, custom range and refresh; `GET /dashboard/overview` returning the vehicle and the period with its comparison window; page-level empty, loading and error states (an unusable custom range in the URL is corrected, never sent); the shared period rules in `packages/shared/src/common/periods.ts`, also used by the Expenses Overview). Phase 2: the section frame and grid; the vehicle hero (quick actions that exist today); the status panel (`vehicle-status.ts`: insurance expiry from the latest insurance payment's policy end, warranty by date or km, whichever first; untracked areas listed, never "healthy"); the metric strip (`metrics.ts`): Spent, Running cost / km, Average mileage, Distance, Fuel spend, each vs the comparison window, from `ExpenseFiguresService` (net totals, odometer distance; the Expenses Overview uses the same readings query) and `FuelService.inWindows` (the full-tank engine's cycles that closed in the window). Phase 3: spending (`spending.ts`: the period by top-level category, and the months around it in the five shared `SpendGroup` series; `ExpenseFiguresService.byCategory`, net, loan principal excluded) and fuel & mileage (the engine's cycles in the period, latest cycle and trend, average price and fuel cost per km from `fuelInWindow`; spend net from Expenses). Phase 4: maintenance (`MaintenanceService.overview`: overdue and due-soon counts, the 4 most urgent schedules, the last service record; a "set up a schedule" card when the vehicle has neither), expiry dates (`expiryDates` in `vehicle-status.ts`, sharing the status panel's insurance and warranty rules: insurance always, "No policy on record" when there's none; the warranty when set) and driving (odometer distance, km per day over the period so far, the latest reading; trips not tracked). Phase 5: the status panel became the action centre (`ActionItem`: state, source and the action that resolves it: "Log service" opens the record form for that schedule, "Add renewal" a new expense; the warranty has none; the 3 most urgent shown, the rest behind "Show N more"), recent activity (`activity.ts`: `ExpenseFiguresService.events` merged with `ServiceRecordsService.recent`, 8 per page) and the "Add service record" quick action. Phase 6: smart insights below the metric strip (Stitch "Dashboard" Smart insights card): spending vs the comparison window with the category that moved most, fuel cost per km over full-tank cycles (with mileage and price behind it), average mileage, mileage falling over the latest full tanks, distance, and maintenance & repairs rising 3 months running. The metrics and spending sections load their figures once and the insights read them; one extra query (spending by category in the comparison window) and `ExpenseFiguresService.firstDate` for the coverage rule. Phase 7: customisation ("Customise" in the header opens a sheet, a bottom sheet on phones): show or hide and reorder the sections below the hero (up/down buttons, each move announced; no drag-and-drop package), choose the key figures, Save / Cancel / Reset to default. The greeting, the vehicle hero and the status panel are fixed (the panel carries overdue obligations). Consecutive small cards (maintenance, expiry dates, driving) share a row. `DashboardLayoutService`, `user_preferences` table (migration `add_user_preferences`). Phase 8: polish. The overview loads each shared source once (records start, the insurance policy, Maintenance's `snapshot` for both the status panel and its card, both windows' figures with one run of the fuel engine), and a service spec checks that a failing source only errors the sections that read it. On phones: 40px tap targets, no horizontal scroll down to 360px, and the vehicle chip keeps a readable minimum width. Card titles are level-2 headings. The loading skeleton is sized like the page and announces "Loading the dashboard…". After an independent review: the key figures follow the same coverage rule as the insights; fuel insights carry their comparison window; the activity feed merges its two sources (each in its own order) instead of re-sorting them, so pages never repeat or skip; focus stays put when a section moves down, on Reset and on Refresh; Customise is off until the saved layout has loaded (a failed load can't overwrite it); key-figure changes say "better"/"worse" to screen readers.

## 5. Web

`features/dashboard/`: from phase 2, one component per section inside a shared section frame (loading skeleton, empty, error with retry, not tracked) and a widget registry in `constants.ts` listing each section (id, title, default order, the module it needs). The period lives in the URL (`use-dashboard-period.ts`, `customWindow` from shared). TanStack Query keys `["dashboard", …]`; fuel, expense and vehicle writes refresh them.
