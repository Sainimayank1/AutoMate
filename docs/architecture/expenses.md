# Expenses (M4): money rules and design

The financial layer of AutoMate. Product scope: [MODULES.md M4](../MODULES.md#module-4--expense-management); API contract: [api-conventions.md](api-conventions.md); data rules: [database.md](database.md).

**Ownership:** the module that owns an operational record stays its source of truth (Fuel owns fill-ups, Maintenance will own service records). Expenses owns the _financial_ view: one expense row per money movement, linked back to its source by `(source, sourceId)`, which is unique, so nothing is counted twice.

## 1. Cost classes and the three money views

Every top-level category has a **cost class**; subcategories inherit it. The class decides which view an expense counts in.

| Cost class  | Examples                                                   | Operating cost | Cash outflow  | Economic ownership cost   |
| ----------- | ---------------------------------------------------------- | -------------- | ------------- | ------------------------- |
| `OPERATING` | Fuel, maintenance, repairs, tolls, parking, washing, other | yes            | yes           | yes                       |
| `OWNERSHIP` | Insurance, PUC, registration, road tax, permits, fines     | no             | yes           | yes                       |
| `FINANCING` | EMI and other loan payments                                | no             | the whole EMI | interest and charges only |
| `CAPITAL`   | Accessories and upgrades                                   | no             | yes           | yes                       |

- **Operating cost** (running cost): what using the vehicle costs. **Cost per km** = operating cost ÷ km driven in the period (from odometer readings; not shown with fewer than two readings). The km run from the last reading before the period, or else from its first reading, and then only cost dated after that first reading counts (it didn't pay for those km).
- **Cash outflow**: everything actually paid, including the full EMI. Excludes the purchase / down payment (shown separately) and unpaid scheduled payments.
- **Economic ownership cost**: operating + ownership + financing charges (interest, processing and prepayment fees) + capital + **depreciation**, always labelled as an estimate (standard Indian motor-insurance depreciation schedule on the purchase price).
- **Loan principal** is cash outflow only: it reduces the loan, it isn't a cost.
- **Refunds** reduce whichever views their original counts in. **Months** are IST calendar months.

## 2. Records

| Rule            | How                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| --------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Money           | `Decimal(12, 2)` in the database, decimal strings in the API, exact integer paise in shared code (`toPaise`, `fromPaise`, `splitEqually`). Never floats.                                                                                                                                                                                                                                                                                                                    |
| Categories      | System tree in `SYSTEM_EXPENSE_CATEGORIES` (`@automate/shared`), seeded by key (`prisma:seed`, idempotent). Users add custom categories and subcategories (unique names among siblings, ignoring case); a used custom category can be disabled but not deleted. Fuel accepts no custom subcategories.                                                                                                                                                                       |
| Fuel            | No manual fuel expenses: fuel comes from fill-ups (phase 2 links them).                                                                                                                                                                                                                                                                                                                                                                                                     |
| Loan payments   | A `FINANCING` expense must carry principal, interest and charges that add up to the amount (checked in shared code, the API and a database CHECK). Finance subcategories preset the split (Loan interest = all interest, Part-prepayment = all principal); a Vehicle EMI is entered split.                                                                                                                                                                                  |
| Shared expenses | Explicit, never assumed: one row per vehicle with a common `sharedGroupId`, split equally (to the paisa, the first vehicles take the spare paise) or by custom shares that must add up. Edited and deleted as one. No odometer, loan split or parts/labour on shared expenses.                                                                                                                                                                                              |
| Refunds         | Their own row (`kind REFUND`, `refundOfId`, reason Refund / Reimbursement / Adjustment); the original is never changed. Total refunds can't exceed the original; a refund can't be dated before it; loan payments aren't refundable. Later edits keep these true: an expense (or its fill-up) can't be lowered below what was refunded, dated after a refund, or moved into Finance while it has refunds (409). Refunds follow their original to a new vehicle or category. |
| Odometer        | One history per vehicle, fill-ups included (through their expenses): a reading can't be below one from an earlier day or above one from a later day (409). A reading raises the vehicle's odometer; correcting it down, removing it or moving the expense to another vehicle lowers the vehicle back to its highest remaining reading.                                                                                                                                      |
| Linked records  | `source` FUEL / MAINTENANCE / TRIP rows are read-only here (409 "Edit it there"); their module creates, updates and deletes them in its own transaction. Bulk actions skip them.                                                                                                                                                                                                                                                                                            |
| Vehicles        | Every write locks the vehicles it touches (in id order) and refuses archived ones; edits, deletes and refunds read the expense again after locking. Bulk actions act on whole shared groups and skip a group with an archived vehicle.                                                                                                                                                                                                                                      |
| Duplicates      | The web sends a client-generated id with every new expense, kept across retries; a create with an id that already exists returns that expense instead of adding one.                                                                                                                                                                                                                                                                                                        |
| Audit           | Every create, update, delete, refund and bulk change writes a structured log line (no amounts or personal data beyond ids).                                                                                                                                                                                                                                                                                                                                                 |

## 4. Phases

Built: **1 · Core** (categories, add / edit / delete / duplicate, transactions with filters, sorting, paging and CSV export, details, shared expenses, refunds, bulk actions, manual loan split), **2 · Fuel link** (§5), **3 · Overview** (KPI strip, category breakdown, recent expenses, monthly trend against last year, upcoming payments; `GET /expenses/summary`, `GET /expenses/trend`) **4 · Recurring payments and the vehicle loan** (§6), **5 · Budgets** (§7) **6 · Ownership cost** (§8), **7 · Insights** (§9) and **8 · CSV import and the printable report** (§10). The module is complete. Receipts are attachments on the expense, shown in its details ([documents.md §2](documents.md#2-files-and-storage)); receipt scanning is out of scope.

## 5. Linked records (Fuel and Maintenance today; Trips later)

`LinkedExpensesService` (exported by `ExpensesModule`) is the only way another module writes money:

- `sync(tx, linked)` creates or updates the expense for `(source, sourceId)`; `remove(tx, source, sourceId)` deletes it (with its refunds). Both run **inside the owning module's write transaction, while it holds the vehicle lock**, so the record and its money never disagree.
- The caller passes system category keys (`FUEL`, `FUEL.PETROL`…), never ids, and the IST calendar date.
- A sync that would lower an amount below what was already refunded against it is refused (409).
- **Fuel:** `toFuelExpense` (`modules/fuel/fuel-expense.ts`) maps a fill-up: title = station (or "Fuel fill-up"), amount = total paid, date = the IST day of the fill-up, subcategory by fuel (Petrol, Diesel, CNG, EV charging; hybrids burn petrol), vendor = station, odometer, description "32.4 L at ₹104.32/L", payment and notes. Create, edit and delete of a fill-up do the same to its expense.
- **Backfill:** migration `link_fuel_expenses` gave every fill-up logged before phase 2 its expense with the same fields (idempotent on the unique key; it also makes sure the Fuel categories exist, since migrations run before the seed).
- **Web:** fuel writes refresh every expense view; expense rows from Fuel link to their fill-up ("Edit in Fuel").
- **Maintenance:** `toMaintenanceExpense` (`modules/maintenance/maintenance-expense.ts`) maps a service record with a cost: title, total, service date, category by record type and work (Repairs, Accessories · Modifications, Washing & detailing, else Maintenance & servicing), workshop as vendor, odometer, and the service details (`service`: type, parts replaced, parts and labour when they fit, warranty, provider). A ₹0 record has no expense. Maintenance also reads the odometer history through `odometerAround` / `highestOdometer` and its links through `expenseIdsFor`; its spending figures come from `ExpensesService.spendByMonth`.
- **Trips:** a trip cost of kind toll, parking or other has one linked expense (source `TRIP`, sourceId = the cost; Daily usage · Toll / Parking, Other · Miscellaneous; title "Toll · Gurugram → Jaipur"), written by `TripCostsService` in the cost's transaction; food and accommodation stay with the trip. Rows from Trips link to `/trips/costs/:costId` ("Edit in Trips"). See [trips.md](trips.md) §1.

## 6. Recurring payments and the vehicle loan

- **A schedule is never a payment.** Nothing is spent until a due date is recorded. Due dates are counted from the start date (`every` × day / week / month / year), so a schedule from the 31st falls on each month's last day. Only dates someone acted on are stored (`RecurringOccurrence`: paid, skipped or postponed); SCHEDULED, DUE (within `reminderDays`) and OVERDUE are worked out on read.
- **Recording** a due date creates the expense in the same transaction (`source RECURRING`, `sourceId` = the occurrence, unique), with the amount, date and method actually paid. That expense is an ordinary, editable expense; deleting it makes the date unpaid again (`expenseId` set to null).
- **Tracked from when it's added.** `activeFrom` is the first due date, or today if that has passed (`trackedFrom`), and resuming a paused schedule moves it to today: dates before it aren't owed and never show as overdue. Overdue looks back at most 366 days.
- **Finance categories** aren't allowed on manual schedules: EMIs come from a loan, which carries the principal / interest split.
- **The loan** (`VehicleLoan`) creates its own EMI schedule (Finance → Vehicle EMI). The amortisation (`loan-schedule.ts`, `Prisma.Decimal`, tested) uses the annuity EMI rounded to the rupee, the last EMI absorbing the rounding; **flat** interest is spread evenly. Recording an EMI books its row's principal and interest. A **prepayment** is a Finance → Part-prepayment expense with `loanId`: it lowers the balance after the EMI on or before its date and keeps the EMI (the tenure shortens). A **rate change** (RBI-style, reducing balance only) applies from its date: keep the EMI and move the tenure, or keep the tenure and change the EMI; when the EMI can't cover the new interest, the tenure is kept.
- **Position** (`outstanding`, `repaid`) counts EMIs due by today or paid early; EMIs before tracking (`beforeTracking`) are assumed paid outside AutoMate and are not expenses.
- **Dashboard:** due and overdue payments appear in the action centre ("Record payment" opens the Recurring tab's dialog).

## 7. Budgets

- A **budget** is a limit for one vehicle per IST **month** (default) or **year**, either overall (no category) or for one **main category** (Fuel included: fill-ups are expenses). One per vehicle and category: a second is refused (409), checked under the vehicle lock because a unique index lets NULL categories repeat. Archived vehicles can't get one.
- **Spent** is worked out on every read, never stored, on the same basis as the dashboard's "Spent": net of refunds, loan principal left out (a Finance budget counts interest and charges). One query covers a page of budgets.
- **State:** `OVER` once spent passes the limit; `WARNING` from `alertPercent` (default 80, 1–100) up to the limit; else `ON_TRACK`. `percent` is whole and rounded down, so 100 means the limit is fully used; `remaining` goes negative when over. Tested in `budget-progress.spec.ts` and `test/budgets.e2e-spec.ts`.
- **Web:** the Budgets tab (`/expenses/budgets`, Stitch "Expenses — Budgets" and "Add Budget Dialog") lists the scope's budgets whole (a handful per vehicle) with counts over, near the limit and on track; add and edit in a dialog, delete after a confirm.
- Not built: budgets across all vehicles, subcategory budgets, rollover of unspent amounts, and alerts outside the Expenses screens.

## 8. Ownership cost

- **Three views** of one vehicle over a period (this month, this year, or since purchase): **operating cost**, **cash outflow** and **economic ownership cost**, as defined in §1. Economic = operating + ownership + financing charges (interest and fees, never principal) + capital + depreciation. Principal is reported apart, inside cash outflow only. One grouped query (`ExpenseFiguresService.byCostClass`) gives every class net of refunds.
- **Depreciation** is always an estimate, on the purchase price and date (none without both): the IRDAI motor-insurance schedule (5% by 6 months, 15% by 1 year, 20/30/40/50% by years 2–5), each step spread evenly over its bracket so periods add up without jumps; after 5 years the schedule stops (values are agreed with the insurer), so no more is estimated (`beyondSchedule`). A period's depreciation is the schedule at its end less at its start (or at the purchase date). Tested in `depreciation.spec.ts` and `test/ownership.e2e-spec.ts`.
- **Web:** the Ownership tab (`/expenses/ownership`, Stitch "Expenses — Ownership"): the three views side by side, where the economic cost goes, per km and per month, and the depreciation card.
- **Per km** is economic cost ÷ km from odometer readings in the period (none with fewer than two); **per month** divides by the calendar months the period spans, at least one.

## 9. Insights

Fixed rules over one vehicle's own records, never AI (`expense-insights.ts`, thresholds in `INSIGHT_RULES`, tested in `expense-insights.spec.ts` and the budgets e2e). The dashboard's smart insights cover period-over-period changes; these add:

- **Budgets** over their limit, then past their warning (from §7).
- **A category above its usual month**: this month so far against the average of the last three full months that have records (two needed), at least 25% and ₹500 above. A category usually at zero isn't flagged (a yearly premium isn't a surprise).
- **Possible duplicates**: two entered (manual or imported) expenses alike in category, amount and day, in the last 90 days. Days apart are left alone (a daily parking fee repeats on purpose).
- **Large one-offs**: this month's expenses (loan payments aside) at least 3× the median expense of the six months before and ₹2,000, when ten or more expenses give a median.

Over-a-limit findings come first, then above-usual, then the rest; each links to where to look. The web tab is `/expenses/insights`.

## 10. CSV import and the printable report

- **Import** reads the columns the CSV export writes, matched by header in any order (Date, Title, Category, Amount (INR) required; Subcategory, Payment method, Vendor, Source and Notes optional; Vehicle is ignored: rows go to the chosen vehicle). Dates are `YYYY-MM-DD` or day first (`21/11/2026`); amounts may carry ₹ and commas; categories match by name or key, subcategories by name; payment methods by value or label.
- **Every row is checked like a manual expense** (`createExpenseSchema`, then the same write path with `source IMPORT`). Not imported: rows the export marks as coming from Fuel, Maintenance, Trips or Recurring (already linked there), refunds (negative amounts: record them on their expense), Fuel (from fill-ups) and loan payments (they need their split). **Duplicates** (same day, amount and category as an expense already recorded, or earlier in the file) wait for "Also import". The preview lists every row that isn't ready (up to 100) and counts them all; the commit re-checks the file and saves in one transaction. Tested in `expense-import.spec.ts` and `test/ownership.e2e-spec.ts`.
- **Limits:** 500 rows and 80 KB, inside the API's 100 KB JSON body limit (500 rows of the export take about 60 KB).
- **The printable report** (`/expenses/report?vehicle=&period=`, Stitch "Expense Report") is a light A4 sheet outside the shell: the three views, by category, by month and every transaction in the period, closed by the cash outflow. The page switches to the light theme while it's open; "Print or save as PDF" uses the browser's dialog. It's opened from the Ownership tab; import is on Transactions, beside Export.
